## 🎯 技术深挖预案（一轮技术面 60-90min）

### 一、组件设计 & 分层架构

**Q1: 为什么要分 commands / core / models / utils 四层？**

> 这是经典的 **关注点分离**：
> - `commands` 是"薄层"，只做参数解析 → 调用 core → 格式化输出
> - `core` 承载业务逻辑，可被多个命令复用（比如 pdf_parser 被 parse/extract/score 共用）
> - `models` 独立出 Pydantic schema，AI 客户端和命令层都依赖它做校验
> - `utils` 放横切关注点（日志、配置），避免循环依赖

**Q2: core 层内部的依赖关系是怎样的？**

> 单向依赖，无循环：
> ```
> commands → core (pdf_parser, ai_client, jd_parser)
>               ↓
>           core/prompts (Prompt 模板)
>               ↓
>           models/schemas (Pydantic 模型)
>               ↓
>           utils (logger, config)
> ```

**Q3: 如果未来要加一个 "批量处理" 命令，架构怎么扩展？**

> 只需在 `commands/` 加一个 `batch.py`，复用 core 层的所有模块。
> 核心逻辑零修改，符合 **开闭原则**。

### 二、状态管理

**Q4: 配置（Settings）是怎么管理的？为什么用单例？**

> - 用 `dataclass` + 模块级变量实现 **懒加载单例**
> - 第一次调用 `get_settings()` 时才加载 .env 和环境变量
> - 单例保证全局配置一致，避免多次重复读取文件
> - `reset_settings()` 用于测试隔离

```python
_settings: Optional[Settings] = None

def get_settings() -> Settings:
    global _settings
    if _settings is None:
        _settings = Settings()  # 此时才读 .env
    return _settings
```

**Q5: .env 加载机制怎么实现的？不用 python-dotenv？**

> 自己实现了一个 30 行的 `_load_dotenv()` 函数：
> - 模块导入时自动调用
> - 支持 `KEY=VALUE`、引号、注释、空行
> - **关键设计**：不覆盖已存在的环境变量（保证优先级）
> - 静默失败（.env 不存在或格式错不影响运行）
>
> 不引入 python-dotenv 是为了 **减少依赖**，CLI 工具越轻量越好。

**Q6: 如果用户同时设置了环境变量和 .env，谁生效？**

> 环境变量优先。因为 `_load_dotenv()` 里：
> ```python
> if key and key not in os.environ:  # 只在未设置时写入
>     os.environ[key] = value
> ```

### 三、性能优化

**Q7: PDF 解析性能如何？**

> - PyMuPDF 是 C 实现，单页 < 0.1s
> - 比 pdfplumber / PyPDF2 快 5-10 倍
> - 实测 814 字符简历，解析时间可忽略

**Q8: AI 调用 10 秒太慢，怎么优化？**

> 当前瓶颈在网络 IO，可以做的优化：
> 1. **流式响应**（已预留接口）：用 `stream=True` 边接收边显示，用户感知更快
> 2. **Prompt 缓存**：把 System Prompt 通过 OpenAI 的 prompt caching 特性复用
> 3. **并发批处理**：多个简历同时提取（asyncio + openai.AsyncOpenAI）
> 4. **小模型降级**：简单简历用 gpt-4o-mini，复杂简历用 gpt-4o
> 5. **本地缓存**：相同 PDF 内容 hash 命中缓存，跳过 AI 调用

**Q9: 如果简历有 50 页怎么办？**

> 当前实现是全部提取 → 全部发给 AI，可能超出 context window。
> 优化方案：
> - 截断到 N 字符（Prompt 中提示 AI 关注前 N 字符）
> - 或分块提取 → 分别提取 → 合并结果（map-reduce 模式）

### 四、错误处理

**Q10: 错误处理体系怎么设计的？**

> 自定义异常层级：
> ```
> PDFError
> ├── FileNotFoundError_   → exit code 1, 提示文件路径
> ├── NotPDFError          → exit code 1, 检查扩展名 + 魔数
> ├── PDFReadError         → exit code 1, PyMuPDF 异常
> └── EmptyPDFError        → exit code 1, 提示可能是扫描件
>
> AIError
> ├── AIConfigError        → 提示设置 OPENAI_API_KEY
> ├── AIResponseError      → 显示原始响应前 300 字符
> └── (网络/超时/限流)      → 分类提示不同解决建议
> ```
>
> 每个命令层统一 try/except，按异常类型输出不同错误信息。

**Q11: 为什么自定义 FileNotFoundError_ 而不是用内置的？**

> 内置的 `FileNotFoundError` 是 Python 标准异常，catch 它可能误伤其他代码。
> 自定义异常继承自 `PDFError`，可以精确 catch PDF 相关错误，不影响其他逻辑。

### 五、AI 集成

**Q12: Prompt 是怎么设计的？**

> **extract 的 System Prompt 关键设计**：
> 1. 角色设定："专业简历信息提取助手"
> 2. 严格 JSON Schema 约束（每个字段类型明确）
> 3. 缺失字段填空字符串，不猜测（避免幻觉）
> 4. temperature=0.1（低温度，输出确定性高）
>
> **score 的 System Prompt**：
> 1. 4 维度评分标准明确（90-100 / 80-89 / ... / 0-59）
> 2. 要求评语 1-3 句话（防止啰嗦）
> 3. 要求 3-5 个面试问题（防止太少或太多）

**Q13: JSON 解析为什么要 4 层容错？**

> AI 模型输出 JSON 不稳定，实测常见问题：
> 1. 直接输出 JSON → 第 1 层 `json.loads()` 即可
> 2. 包裹 markdown 代码块 → 第 2 层正则提取
> 3. 前后有废话文字 → 第 3 层定位 `{}`
> 4. 末尾逗号、单引号 → 第 4 层修复
>
> 这种渐进式容错比强制 JSON mode 更鲁棒，兼容所有模型。

**Q14: 怎么保证 AI 返回的数据类型正确？**

> Pydantic v2 二次校验：
> ```python
> validated = ResumeData(**result_data)
> result_dict = validated.model_dump()
> ```
> 即使 AI 返回了多余字段或错误类型，Pydantic 会自动过滤/转换。

### 七、加分题

**Q17: 如果要把这个 CLI 改成 Web 服务，怎么改？**

> 架构已分层，改动很小：
> 1. 保留 `core/` 全部模块（业务逻辑零修改）
> 2. 保留 `models/` 全部模型
> 3. 用 FastAPI 替换 `commands/`，每个命令变成一个 endpoint
> 4. 上传 PDF → 调用 `extract_text_from_pdf()` → 调用 `call_ai_json()` → 返回 JSON
>
> 这就是分层架构的价值——核心逻辑与入口形式解耦。
